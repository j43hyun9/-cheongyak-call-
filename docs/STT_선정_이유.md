# **STT 엔진 선정 이유**

작성: 임강 · 2026-08-20, 커밋 2026-08-21 (초안 — 팀 리뷰 대기) 목적: 발표 Q&A 대비 + 팀 기록. `docs/발표_예상질문.md`에 Q9으로 편입할지는 검토 후 결정.

## **결론 요약**

콜비 STT는 **엔진 추상화 구조**로 2가지를 선택적으로 씀 (`backend/stt.py`, `STT_ENGINE` 설정값):

| **엔진** | **언제** | **이유** |
| --- | --- | --- |
| `openai` (Whisper API) | 기본값, 1차부터 채택 | 도메인 힌트 프롬프트 지원, 클라우드라 팀 하드웨어 무관 |
| `local` (faster-whisper) | 3차(8/14) 추가 | GPU 없는 팀 환경에서도 무료·오프라인 서빙 가능 |

두 엔진을 없애지 않고 **공존**시킨 건 `backend/llm.py`(openai/local/perso)와 동일한 추상화 패턴을 따른 것 — 하나가 막혀도 다른 쪽으로 폴백 가능하고, 나중에 완전 로컬 자율 서빙으로 갈 여지를 열어둠.

---

## **1. 1·2차 — Whisper API 채택**

### **확정된 이유**

1. **한국어 인식률**: 1차 시점에 조사했을 때 Whisper API의 한국어 인식률이 좋은 편이었음
2. **강사 추천 기술 스택**: 당시 강사가 추천한 기술 스택에 OpenAI Whisper API가 포함되어 있었음
3. **3차에서의 재사용 이유(별개)**: 3차에서 STT를 다시 붙일 때는 재조사 없이 그대로 재사용 — **결제해둔 OpenAI 토큰이 남아있어서** 별다른 고민 없이 1·2차와 동일한 선택을 이어감

즉 1·2차 채택 이유는 "인식률+강사 추천"이지만, **3차 재사용은 그 이유를 다시 검토한 게 아니라 순전히 남은 토큰 때문** — 이 구분이 발표 Q&A에서 중요함("3차에도 왜 Whisper냐"는 질문엔 "1·2차 검증 + 토큰 재사용"이 정확한 답).

### **참고 — 레포에서 확인되는 정황 (보조 근거)**

- 1차 로컬 작업 폴더에 `stt_google.py`(SpeechRecognition+Google 웹 음성인식, 무료)도 실험 파일로 있었지만 **레포에 커밋된 건 Whisper 버전(`stt.py`)뿐** — 위 1번(한국어 인식률) 이유와 일치하는 정황
- 커밋 메시지(`ab466d5`)엔 "Add speech-to-text conversion function using Whisper"만 적혀있고 선정 이유 자체는 문서화된 적 없었음 — 이번에 당사자 확인으로 채워짐
- 참고로 2차(`project2`) API 계약(`CLAUDE.md`)엔 `/stt` 엔드포인트가 정식으로 없었음 — 2차 시점 Whisper 활용은 정식 기능이 아니라 내부적으로 계속 유지·검토하던 상태였던 것으로 보임(3차에서 `/stt`로 정식 API화)

## **2. 3차 (8/14, PR#14) — faster-whisper 로컬 엔진 추가**

### **문서화된 이유 (`docs/API_STT_초안.md` 설계 메모, PR#14 본문)**

1. **GPU 없는 팀 환경 가정** — `faster-whisper`를 `device="cpu", compute_type="int8"`로 고정. 개인 PC에서도 무리 없이 돌아가게 하려는 목적.
2. **비용/의존성**: 로컬 엔진은 API 비용 없이 오프라인으로 동작 — 클라우드 키 없이도 데모 가능.
3. **`llm.py`와 동일한 엔진 추상화 패턴** 재사용 — 팀 코드베이스 일관성.
4. 기존 `openai` 엔진과 `/stt` API 계약(`{text}`)은 그대로 유지 — 엔진 선택은 내부 구현 디테일로, 프론트/타 API에 영향 없음.

### **검증 결과 (PR#14)**

- gTTS로 생성한 한국어 음성으로 정확도 확인(정확히 인식)
- 첫 실행은 모델 다운로드 포함 182초, 캐시 이후 1.5초/요청 — 실사용 가능한 속도

## **3. 실측 비교 — Whisper API vs faster-whisper (2026-08-20, 임강)**

### **방법**

- gTTS로 도메인 문장 4개를 한국어 음성으로 생성(`.stt_bench/*.mp3`, 레포에 커밋 안 함 — 벤치용 임시 파일)
- 동일 오디오를 `backend/stt.py`의 두 엔진 경로로 그대로 통과시켜 비교 (도메인 힌트 프롬프트 동일하게 적용)
- Whisper API는 이번 벤치 한정으로 실키를 `.env`에 임시로 넣어 테스트 후 즉시 더미로 복구(레포에 실키 커밋된 적 없음)

### **결과**

| **샘플** | **원문** | **Whisper API (`whisper-1`)** | **faster-whisper (`base`, CPU int8)** |
| --- | --- | --- | --- |
| basic | 공모주 청약 일정 알려줘 | 공모주, 청약, 일정 알려줘. ✅ | 공모주 청약 일정 알려줘. ✅ |
| name | 기도산업 청약 일정 알려줘 공모가는 얼마야 | **완전 일치** ✅ | "국무관은 얼마야?" ❌ (공모가→국무관) |
| number | 균등배분이랑 비례배분 차이 설명해줘 | 균등 배분이랑 비례배분 차이 설명해줘. ✅ | "빈 등 배분이라 빈 배분 차이" ❌ (전문용어 붕괴) |
| slang | 따상이 뭐야 | "빠상이 뭐야?" ❌ (오인식하나 발음 유사) | "따 3이 뭐야?" ❌ (숫자로 오인식) |

**지연시간**: Whisper API 1000-2250ms(네트워크 왕복 포함) vs faster-whisper 468-1562ms(로컬, 모델 로드 687ms 별도)

### **해석**

- **전문용어(공모가·균등배분·비례배분) 정확도는 Whisper API가 확실히 우위** — `base` 크기 faster-whisper는 도메인 힌트 프롬프트를 넣어도 한계가 뚜렷함(더 큰 모델 `small`/`medium`으로 올리면 개선될 여지는 있으나 CPU 추론 속도가 그만큼 느려짐 — 트레이드오프)
- **슬랭("따상")은 둘 다 실패** — 이건 모델 크기보다 학습 데이터에 이 단어 자체가 거의 없어서일 가능성이 높음. STT보다는 **RAG concept 문서에 "따상" 발음 변형까지 커버**하는 쪽이 더 현실적인 해법으로 보임
- **지연시간은 상황에 따라 다름**: 로컬 CPU는 요청당 절대 시간은 짧지만, 여러 요청이 겹치면 CPU 자원을 나눠 써야 해서 확장성은 API 쪽이 유리할 수 있음
- 결론적으로 **"정확도 우선이면 openai, 오프라인/무료가 우선이면 local"**이라는 기존 엔진 추상화 설계가 실측으로도 합리적임이 확인됨

## **4. Deepgram 검토 (멘토링 추천, 2026-08-13)**

멘토링 강사가 Deepgram을 추천함. 웹 검색으로 확인한 내용과 우리 프로젝트에 대입한 판단:

- Deepgram의 핵심 강점은 **실시간 스트리밍 저지연**(sub-300ms, WebSocket 기반 partial transcript) — Whisper API/faster-whisper는 둘 다 파일 전체를 업로드/처리하는 **배치 방식**
- 그런데 CLAUDE.md **"주요 설계 결정"**에 이미 명시돼 있음: **"통신: 동기 요청/응답 `/chat` 한 번에 반환 — WebSocket/SSE 스트리밍 사용 안 함"** — 우리 프로젝트는 애초에 스트리밍 아키텍처를 안 쓰기로 결정된 상태
- 즉 지금 구조(파일 업로드 배치)에 Deepgram만 갈아끼우면 **Deepgram의 진짜 강점을 못 살리고, 체감 차이도 크지 않을 가능성이 높음**. 진짜 이점을 보려면 `/stt`를 WebSocket 기반으로 재설계해야 하는데, 이는 기존 설계 결정을 뒤집는 큰 변경이라 임강 단독 판단 범위를 벗어남(PM 협의 필요)
- **[업데이트, 아래 5-2 참고] 한국어 기준 CER 벤치마크를 찾음 — Deepgram(nova-2)이 21.18%로 조사한 10개 서비스 중 최하위.** 스트리밍 구조 미스매치뿐 아니라 **순수 한국어 인식 정확도 자체도 이 프로젝트엔 안 맞는 선택**이라는 근거가 추가됨.

**결론**: 방향 자체("AI Human 실시간 대화감")는 타당한 제안이었지만, ① 마감(8/24)까지 남은 기간, ② 기존 설계 결정("스트리밍 안 씀"), ③ 한국어 CER 실측 최하위 3가지가 겹쳐서 **이번 프로젝트 범위에서는 채택 보류**로 결론. 다음 프로젝트나 실서비스 확장 시 스트리밍 아키텍처로 갈 때 (Deepgram 말고 다른 후보로) 재검토 대상으로 남겨둠.

## **5. 다른 STT 서비스 비교 조사 (2026-08-20, 웹 조사)**

발표/기록용으로 이름있는 STT들을 카테고리별로 조사. **주의**: 아래는 대부분 공개 자료·벤치마크 인용이라 실측(3번)만큼의 신뢰도는 아님 — 특히 벤더 자체 발표 수치는 자사 유리하게 편향될 수 있음.

### **5-1. 글로벌 빅테크 (Google Cloud STT, Azure AI Speech, AWS Transcribe)**

|  | **Google Cloud STT (Chirp)** | **Azure AI Speech** | **AWS Transcribe** |
| --- | --- | --- | --- |
| 가격(실시간) | $0.016/분 | 약 $0.017/분($1/시간) | $0.024/분 |
| 배치 가격 | $0.004/분(75%↓) | $0.003/분($0.18/시간) | 대량 시 $0.0078/분까지↓ |
| 무료 티어 | 월 60분 | - | - |
| 커스텀 용어사전 | 지원 | 지원(Custom Speech, 별도 학습비) | 지원 |
| 한국어 CER(아래 5-2 실측) | 11.59% (10개 중 8위) | 10.88% (5위) | 11.11% (6위) |

**커스텀 보캐뷸러리 기능**이 셋 다 있음 — "따상" 같은 슬랭을 사전 등록하면 우리가 겪은 인식 실패를 해결할 수 있는 잠재력. 다만 Whisper API($0.006/분)보다 다 비싸고, 아래 실측 CER상 정확도도 우리가 쓰는 Whisper API(11.34%)보다 나은 게 없음 — **가격도 정확도도 우위 없어 채택 매력 낮음.**

### **5-2. 한국어 특화 (네이버 클로바, 카카오, ETRI, 리턴제로)**

`rtzr/Awesome-Korean-Speech-Recognition`(리턴제로 자체 공개 벤치마크, AI-Hub 6개 데이터셋·서비스당 3000문장 샘플링, CER 기준)에서 **10개 서비스 전체 순위**를 찾음:

| **순위** | **서비스** | **평균 CER** |
| --- | --- | --- |
| 1 | **리턴제로(RTZR) 자체 엔진** | **5.91%** |
| 2 | 리턴제로 Whisper(자사 튜닝) | 6.59% |
| 3 | **네이버 클로바 스피치** | **7.52%** |
| 4 | ETRI 공공 AI | 10.19% |
| 5 | Azure Batch STT | 10.88% |
| 6 | AWS Transcribe | 11.11% |
| **7** | **OpenAI Whisper (우리가 쓰는 것)** | **11.34%** |
| 8 | Google Speech v2 | 11.59% |
| 9 | Gemini 2.0 Flash | 14.48% |
| 10 | Deepgram (nova-2) | 21.18% |

**⚠️ 주의**: 출처가 1위인 리턴제로 자사 발표 자료라 자사 유리 편향 가능성 있음. 다만 방법론(AI-Hub 공개 데이터셋, CER 공식, 3000문장 샘플)이 투명하게 공개돼 있고, 순위 자체(한국어 특화 엔진 > 글로벌 빅테크 > Deepgram)는 일반적으로 알려진 경향과도 일치해서 대략적인 참고는 가능하다고 판단.

**우리 프로젝트에 대입하면**: **우리가 쓰는 OpenAI Whisper API(11.34%)가 10개 중 7위** — 나쁘진 않지만 한국어 특화 엔진(리턴제로 5.91%, 네이버 클로바 7.52%) 대비 오차율이 거의 2배. 만약 정확도를 최우선으로 개선하고 싶다면 **네이버 클로바 스피치(CSR)로 교체하는 게 가장 현실적인 업그레이드**로 보임 — 국내 서비스라 한국어 도메인(공모주 용어)에 유리할 가능성 높고, NAVER Cloud Platform 콘솔에서 바로 발급 가능. 카카오는 최신 가격/성능 공개자료를 못 찾음(2019년 자료뿐), 엔터프라이즈 "커스텀 STT" 별도 상품이 있다는 것만 확인.

#### **RTZR(리턴제로) 딥다이브 — CER(Character Error Rate,문자 오류율) 1위라 추가 조사**

**회사**: 2018년 설립, 2026년 기준 **시리즈C까지 투자 유치**(최근 50억원, 우리벤처파트너스·신한벤처투자). **금융권 AICC(AI 콜센터)·공공기관에 B2B로 이미 납품 중** — 자사 벤치마크(위 CER표 출처)라 편향 우려는 있지만, 실제 상용 레퍼런스가 있어 신뢰도를 어느 정도 뒷받침함. 자체 엔진이 1,500만 시간 이상 한국어 음성 데이터로 학습됐다고 주장.

**API 특징**:

- **실시간 스트리밍 + 파일 업로드(배치) 둘 다 지원** — Deepgram과 달리 지금 우리의 배치(파일 업로드) 구조를 그대로 유지하면서 엔진만 교체 가능(CLAUDE.md "스트리밍 안 씀" 결정과 충돌 없음)
- **"화자분리, 키워드 부스팅" 기능 명시** — **키워드 부스팅이 정확히 우리가 실측(3번)에서 겪은 "따상"→"따 3"/"빠상" 오인식 문제의 해법**으로 보임. 도메인 용어(따상·균등배분·공모가 등)를 사전 등록해 인식 우선순위를 높이는 기능
- 무료 체험 제공, 상세 기술 명세는 `developers.rtzr.ai`(이번 조사에서 페이지 접근은 됐지만 구체 엔드포인트 스펙까지는 확인 못 함 — 실측 시 재확인 필요)

**가격**: STT API 10시간 무료 → 이후 **시간당 1,000원 종량제**(Whisper API는 시간당 약 500원 수준이라 상대적으로 비싸지만, 10시간 무료면 학생 프로젝트 데모엔 충분).

**종합 판단**: 정확도 1위 + 슬랭 문제에 정확히 맞는 키워드 부스팅 + 배치 구조 그대로 호환 + 무료 티어 — 4가지가 겹쳐서 **네이버 클로바보다 오히려 더 구체적으로 끌리는 후보**. 다만 벤치마크가 자사 발표라는 점, 스타트업이라 대기업(네이버) 대비 API 안정성·문서 완성도 검증이 덜 됐을 수 있다는 점은 감안.

### **5-3. 오픈소스/로컬 대안 (NVIDIA Parakeet, Whisper large-v3-turbo, SenseVoice)**

우리가 쓰는 `faster-whisper`(base, CPU)의 대체/업그레이드 후보:

|  | **한국어 지원** | **라이선스** | **특징** |
| --- | --- | --- | --- |
| **NVIDIA Parakeet** | ❌ **미지원** (유럽어 25개 언어만) | CC-BY-4.0 | **한국어 프로젝트엔 애초에 후보가 안 됨** |
| **Whisper large-v3-turbo** | ✅ | MIT | large-v3 대비 속도 5배, 정확도 큰 손실 없음 — 지금 쓰는 `base`보다 정확도↑ 기대되지만 모델 크기 커서 CPU 메모리·속도 트레이드오프 있음 |

### **5-4. STT 전문 스타트업 (AssemblyAI, Speechmatics)**

- 둘 다 **한국어 특화 벤치마크 공개 자료를 못 찾음** — 이 자체가 시그널: 두 회사 다 마케팅 포인트가 영어권 실시간 콜센터·회의록 시장이라 한국어는 우선순위가 아닌 것으로 보임
- 일반(비한국어) 비교에서는 Speechmatics가 노이즈·다화자 환경에서 AssemblyAI보다 우세하다는 자료가 있었음(G2 리뷰 기준 90% vs 80%)
- **결론**: 한국어 도메인 프로젝트엔 근거 부족 — 실측 없이 채택 판단하기엔 정보가 너무 없음. 우선순위 낮음.

## **6. 실측 2차 — SenseVoice 로컬 검증 (2026-08-20, 임강)**

### **방법**

- `funasr`(1.4.2) + `iic/SenseVoiceSmall`(936MB, ModelScope) 로컬 설치 후 3번과 동일한 4개 오디오 샘플로 검증
- **삽질 기록**: 최초 실행 시 Windows 사용자 폴더 경로에 한글("이스트캠프")이 포함돼 있어 sentencepiece가 토크나이저 모델 파일을 못 여는 인코딩 버그(`Illegal byte sequence Error #42`) 발생 → 다운로드된 모델을 ASCII 전용 경로(`.stt_bench/models/SenseVoiceSmall`)로 복사해서 해결. **한글 Windows 사용자명 환경에서 흔히 겪는 문제라 팀 공유 가치 있음**(다른 팀원도 로컬 개발 시 비슷한 라이브러리에서 걸릴 수 있음).

### **결과**

| **샘플** | **원문** | **SenseVoiceSmall** | **참고: Whisper API** | **참고: faster-whisper** |
| --- | --- | --- | --- | --- |
| basic | 공모주 청약 일정 알려줘 | 공모주 청약 일정 알려줘. ✅ | 공모주, 청약, 일정 알려줘. ✅ | 공모주 청약 일정 알려줘. ✅ |
| name | 기도산업 청약 일정 알려줘 공모가는 얼마야 | "기도 산업 청약 일정 알려줘어 **공무 관**은 얼 마야." ❌ | **완전 일치** ✅ | "**국무관**은 얼마야?" ❌ |
| number | 균등배분이랑 비례배분 차이 설명해줘 | 균등 배분 이랑 비례 배분 차이 설명 해 줘. ✅ (띄어쓰기만 차이) | 균등 배분이랑 비례배분 차이 설명해줘. ✅ | "빈 등 배분이라 빈 배분" ❌ |
| slang | 따상이 뭐야 | "**빠 상**이 뭐야." ❌ | "빠상이 뭐야?" ❌ (SenseVoice와 동일 오류) | "따 3이 뭐야?" ❌ |

**지연시간**: SenseVoice **187-342ms** (모델 로드 1906ms 별도) — Whisper API(1000-2250ms)의 약 1/6-1/8, faster-whisper(468-1562ms)보다도 2-3배 빠름.

### **해석**

- **속도는 압도적** — 조사 단계(5-3)에서 본 "Whisper-Large 대비 15배 빠름" 주장이 실측에서도 체감됨. CPU에서 200-350ms면 실사용에 전혀 무리 없는 수준
- **정확도는 Whisper API와 거의 동급** — "공모가"를 놓친 건 SenseVoice만의 약점(faster-whisper와는 다른 방식으로 틀림), "따상"은 Whisper API와 **똑같이 "빠상"으로 틀림**(우연이 아니라 발음이 실제로 유사해서 나오는 공통 오류로 보임) — 슬랭 문제는 어느 로컬/클라우드 엔진을 쓰든 STT 레벨에서 해결 안 될 가능성이 높다는 근거가 하나 더 늘어남 (→ [[RAG concept 문서 보강]] 쪽이 정공법이라는 3번 결론 재확인)
- **`base` 크기 faster-whisper보다 종합적으로 우위** — 속도도 빠르고, 전문용어 오류 패턴도 더 가벼움(단어 하나만 틀림 vs 문장 전체 붕괴)

### **결론**

**local 엔진을 `faster-whisper`에서 `SenseVoice`로 교체하는 걸 실측 근거로 추천할 수 있음.** 다만:

- `backend/stt.py`의 엔진 추상화 구조에 새 엔진을 끼워 넣는 코드 작업이 필요(현재는 openai/local 두 개뿐)
- `funasr` 의존성이 무겁고(`torch`+`torchaudio` 추가 설치 필요), 모델 파일도 936MB — 팀원 전원의 로컬 환경에 영향(requirements.txt·다운로드 시간)
- Windows 환경에서 사용자명에 한글이 있으면 위 버그를 겪을 수 있음 — 팀원 중 해당하는 사람 있으면 미리 공유 필요
- **실제 교체는 코드 변경(임강 담당 영역)이라 진행 여부는 별도 결정 필요** — 이 문서는 근거 정리까지만, 실행은 아직 안 함

## **7. 정리 — 발표 대응용 한 줄 답변**

"1·2차 때 조사 시점 한국어 인식률이 좋고 강사 추천 기술 스택에도 있어서 OpenAI Whisper API를 채택했고, 3차에서는 결제해둔 토큰이 남아있어서 재조사 없이 그대로 재사용했습니다. 대신 GPU 없는 팀 환경도 지원하기 위해 faster-whisper 로컬 엔진을 엔진 추상화 구조로 추가했습니다. 실측해보니 전문용어 정확도는 Whisper API가 우위, 지연은 로컬이 더 짧아서 상황별로 고를 수 있게 뒀습니다. 발표 준비하면서 Deepgram·네이버 클로바·리턴제로·구글/애저/AWS·오픈소스 대안까지 조사했는데, 한국어 CER 실측 기준으로는 Whisper가 10개 중 7위(중위권)로 나쁘지 않은 선택이었습니다. 로컬 엔진은 SenseVoice로 실측까지 해봤는데, faster-whisper보다 속도·정확도 모두 우위라 다음 개선 후보로 남겨뒀습니다. Deepgram은 스트리밍 구조 미스매치에 더해 한국어 CER도 최하위라 채택하지 않았고, '따상' 같은 슬랭은 어떤 STT 엔진을 쓰든 실패해서 RAG 쪽 보강이 더 정공법이라고 판단했습니다."

## **남은 과제**

- 1차 Whisper vs Google 비교의 레포 근거(1번 절 하단)는 **당사자 확인으로 뒷받침됨** — 다만 Google 엔진 자체의 실측 비교는 여전히 안 함(필요시 추가 가능)
- **네이버 클로바·리턴제로(RTZR)는 API 키 발급이 필요해 이번 라운드는 보류**(사용자 결정, 2026-08-20) — 5-2 절 공개 자료 기준 정리(CER 3위·1위)만 있고 우리 도메인 문장 실측은 아직 안 함. 나중에 키 발급하면 3·6번과 동일한 4개 샘플로 이어서 검증 가능
- **SenseVoice 로컬 엔진 교체는 근거만 정리됨, 실제 코드 반영은 아직 안 함** — 진행하려면 `backend/stt.py`에 세 번째 엔진 옵션 추가 + `requirements.txt`(funasr/torchaudio) 반영 필요
- 2026-08-21 `docs/`에 커밋해 팀 공유. `발표_예상질문.md`에 Q9으로 편입할지는 아직 미결.
- `.stt_bench/` 폴더(테스트 오디오·스크립트·결과 JSON·SenseVoice 모델 936MB)는 벤치용 임시 산출물 — 레포에 커밋 안 함. 특히 모델 파일이 커서(936MB) 디스크 정리 필요하면 알려주면 지움
